# Единая база: Продажи · Склад · Производство

CRM для металлообработки и поставки трубопроводной арматуры: сделки, конструктор
спецификаций с подбором аналогов, жёсткие резервы, снабжение с контролем сроков,
производство по 7 стадиям и реальная себестоимость каждого проекта.

**Стек:** Next.js 15 (App Router, Server Actions) + Supabase (Postgres, Auth, Storage, RLS) → деплой на Vercel.

---

## 1. Что уже реализовано

### Продажи
- Сделки со сквозными этапами: Заявка → Расчёт → КП → Договор → Снабжение → Производство → ОТК → Отгрузка.
- Автоматический номер сделки, история этапов с замером длительности каждого.
- Источники заявок: сайт, тендер, звонок, почта, WhatsApp, рекомендация.
- **Конструктор спецификаций**: версии, разделы, себестоимость/цена по строке, автоматический пересчёт итогов, наценка, скидка, НДС, максимальный срок поставки.
- **Подбор аналогов**: справочник взаимозамен с уровнем совместимости; замена прямо в сделке с фиксацией причины, характера (временная/постоянная), даты возврата штатной позиции и автоматическим пересчётом сметы. Всё пишется в журнал замен.
- Автогенерация КП (печатная форма → Ctrl+P → PDF), статусы Черновик → Отправлено → Принято/Отклонено.
- Оплаты по сделке; предоплата открывает жёсткий резерв.

### Склад и снабжение
- Три зоны: основной склад материалов, цех (материал «в работе»), склад готовой продукции. Зоны добавляются в настройках.
- Номенклатура с комбинированными единицами (т, лист, шт, м, м², компл, нормо-час), марками стали 304/316/316L/09Г2С, ГОСТами и техническими характеристиками (JSON).
- Пересчёт «лист ↔ тонна» через таблицу `item_units`.
- **Партии прихода с номером плавки и сертификатом**; для критичных позиций приёмка без сертификата блокируется. Файлы — в Supabase Storage, прослеживаемость «плавка → заказ» в отчёте.
- **Резервы двух типов:**
  - *информационный (soft)* — на этапе КП, показывает плановый расход;
  - *жёсткий (hard)* — только при предоплате либо по договору с ключевым клиентом (правило зашито в БД, обойти из интерфейса нельзя).
- **Снятие жёсткого резерва — только через согласование директора.** Менеджер или снабженец оформляет заявку с причиной; директор разрешает или отклоняет в разделе «Задачи». Прямое удаление резерва заблокировано триггером.
- **Лист дефицита** формируется одной кнопкой из спецификации, превращается в заявку в закуп и задачу отделу снабжения.
- Заказы поставщикам со статусами Заказано → Оплачено → В пути → На складе, датами по каждому статусу и контролем просрочки.
- Приёмка позиции заказа создаёт партию, сертификат и приход на склад одной операцией.
- **Неснижаемый остаток**: как только остаток падает ниже минимума, система сама создаёт задачу снабжению (и закрывает её, когда запас восстановлен).

### Производство
- Маршрутный лист со штрихкодом, комплектация из спецификации.
- 7 контролируемых стадий: Ожидание комплектующих → Заготовительный участок → Сварка и сборка → Комплектация и монтаж → ОТК → Покраска/антикор → Готово к отгрузке (+ Отгружено).
- **Запуск в цех запрещён, если комплектующих нет на складе** — переход со стадии «Ожидание комплектующих» блокируется на уровне БД с перечислением недостающих позиций.
- Выдача материалов в цех списывает партии по FIFO с сохранением прослеживаемости плавок и переводит резервы в статус «израсходован».
- Переход по стадиям — кнопкой или сканированием штрихкода в режиме «Цех» (страница `/production/scan`, оптимизирована под планшет). Каждый переход пишет длительность предыдущей стадии.
- ОТК: виды контроля (швы, опрессовка, проверка задвижек…), результат, замечания; без отметки ОТК заказ дальше не пройдёт. Паспорта изделий подгружаются в карточку.
- При достижении «Готово к отгрузке» менеджеру автоматически ставится задача связаться с клиентом.

### Аналитика и интеграции
- Реальная себестоимость проекта: план (спецификация) vs факт (списанные материалы по фактической цене партий + прочие затраты), отклонение, маржа.
- Средняя и медианная длительность каждого этапа сделки и каждой стадии производства — для планирования сроков.
- Отчёт по влиянию замен на смету и по просроченным возвратам временных подмен.
- **Открытый REST-API для выгрузки в Grok / Gemini / BI** — JSON и CSV, см. раздел 6.

## 2. Роли

| Роль | Что видит и делает |
|---|---|
| **Директор** | Всё. Дашборды рентабельности, согласование снятия резервов, пользователи, настройки |
| **Менеджер по продажам** | Сделки, спецификации, КП, резервы, склад (просмотр), производство (просмотр) |
| **Снабжение / закуп** | Дефицит, заявки, заказы поставщикам, приёмка, склад, номенклатура |
| **Начальник производства** | Доска цеха, маршрутные листы, стадии, ОТК, склад (просмотр) |
| **Кладовщик** | Склад, партии, движения, приёмка |

Доступ к данным ограничен политиками RLS на уровне Postgres: читают общие данные все (принцип «единого окна»), изменяют — только профильные роли.

## 3. Запуск: Supabase

1. Создайте проект на [supabase.com](https://supabase.com) (регион ближе к вам, напр. `eu-central-1`).
2. Откройте **SQL Editor** и выполните файл `supabase/schema.sql` целиком (это все миграции подряд).
   Либо по одному файлу из `supabase/migrations/` в порядке нумерации.
   Если у вас установлен Supabase CLI: `supabase link --project-ref <ref>` затем `supabase db push`.
3. Проверьте **Storage** — должны появиться приватные бакеты `certificates`, `documents`, `photos`.
   Если политики доступа не создались (миграция напишет `notice`), добавьте их вручную:
   Storage → Policies → для каждого бакета разрешить `select/insert/update` роли `authenticated`.
4. Создайте первого пользователя-директора: **Authentication → Users → Add user**
   (email + пароль, галочка *Auto Confirm User*). Затем в **SQL Editor**:

   ```sql
   update public.profiles
      set role = 'director', full_name = 'Ваше ФИО'
    where id = (select id from auth.users where email = 'ваш@email');
   ```

   Дальше остальных сотрудников заводите прямо в интерфейсе: **Настройки → Новый пользователь**.
5. Скопируйте из **Project Settings → API**: `Project URL`, `anon/publishable key`, `service_role key`.

## 4. Запуск локально

```bash
npm install
cp .env.example .env.local   # и заполните значения
npm run dev
```

`.env.local`:

```
NEXT_PUBLIC_SUPABASE_URL=https://<ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon key>
SUPABASE_SERVICE_ROLE_KEY=<service role key>
CRM_API_KEY=<любой длинный случайный ключ для выгрузок>
```

Откройте http://localhost:3000 и войдите под созданным директором.

## 5. Деплой на Vercel

1. Залейте папку в репозиторий Git и импортируйте его в Vercel (framework определится как Next.js).
2. В **Project Settings → Environment Variables** добавьте те же 4 переменные
   (`SUPABASE_SERVICE_ROLE_KEY` и `CRM_API_KEY` — **без** префикса `NEXT_PUBLIC_`).
3. Deploy. Миграции применяются в Supabase отдельно (раздел 3), Vercel их не трогает.

Через CLI:

```bash
npm i -g vercel
vercel link
vercel env add NEXT_PUBLIC_SUPABASE_URL
vercel env add NEXT_PUBLIC_SUPABASE_ANON_KEY
vercel env add SUPABASE_SERVICE_ROLE_KEY
vercel env add CRM_API_KEY
vercel --prod
```

## 6. API выгрузки данных

Ключ передаётся заголовком `x-api-key` или параметром `?key=`.

```
GET /api/v1                                   — список эндпоинтов
GET /api/v1/export/deals                      — сделки: выручка, план/факт себестоимости, маржа
GET /api/v1/export/specifications             — строки спецификаций
GET /api/v1/export/substitutions              — замены и подмены, влияние на смету
GET /api/v1/export/stock                      — дефицит и неснижаемые остатки
GET /api/v1/export/balances                   — остатки, резервы, свободное количество
GET /api/v1/export/purchases                  — заказы поставщикам и сроки
GET /api/v1/export/production                 — производственные заказы и переходы стадий
GET /api/v1/export/stage-durations            — длительность стадий производства
GET /api/v1/export/deal-stage-durations       — длительность этапов сделок
GET /api/v1/export/moves                      — движения по складу с плавками
GET /api/v1/export/counterparties, /items     — справочники
```

Параметры: `format=json|csv`, `from=YYYY-MM-DD`, `to=YYYY-MM-DD`, `limit=1..50000`.

Пример:

```bash
curl -H "x-api-key: $CRM_API_KEY" \
  "https://<ваш-домен>/api/v1/export/deals?format=csv&from=2026-01-01" -o deals.csv
```

Дополнительно доступен родной REST/GraphQL Supabase (PostgREST) — с ключом `service_role` можно читать любые таблицы и представления напрямую.

## 7. Как работает сквозная цепочка

1. **Заявка.** Менеджер создаёт сделку, указывает клиента, источник и ТЗ. Автоматически создаётся спецификация v1.
2. **Расчёт.** В конструкторе набирается спецификация. Рядом с каждой строкой видно свободный остаток на складе. Если нужной позиции нет или поставка задерживается — кнопка «⇄» открывает подбор аналога: видно разницу в цене, сроке и наличии. Замена фиксируется с причиной и датой возврата, смета пересчитывается сразу.
3. **КП.** Одной кнопкой формируется коммерческое предложение из текущей версии спецификации, печатается в PDF.
4. **Договор и оплата.** Вносится предоплата → открывается право на жёсткий резерв.
5. **Снабжение.** Кнопка «Жёсткий резерв под заказ» резервирует всё, что есть на складе; кнопка «Сформировать лист дефицита» создаёт заявку в закуп и задачу снабженцу. Снабженец делает заказ поставщику и ведёт его по статусам до прихода на склад; приёмка создаёт партию с плавкой и сертификатом.
6. **Производство.** Из сделки создаётся маршрутный лист. Пока комплектация не собрана, стадия «Ожидание комплектующих» не переключается. После выдачи материалов мастер ведёт заказ по стадиям (кнопка или скан штрихкода).
7. **ОТК и отгрузка.** Фиксируются проверки, подгружаются паспорта. На стадии «Готово к отгрузке» менеджеру приходит задача связаться с клиентом; оформляется отгрузка.
8. **Итог.** В карточке сделки, вкладка «Себестоимость» — план, факт, отклонение и маржа с расшифровкой по материалам, закупу и прочим затратам.

## 8. Структура проекта

```
app/
  (app)/                     защищённая часть (layout проверяет сессию)
    page.tsx                 дашборд
    deals/                   сделки: обзор, спецификация, КП, снабжение, цех, себестоимость
    catalog/                 номенклатура, аналоги, цены поставщиков
    warehouse/               остатки, партии/сертификаты, движения
    procurement/             дефицит, заявки, заказы поставщикам
    production/              доска цеха, маршрутный лист, режим сканирования
    counterparties/          клиенты и поставщики
    tasks/                   задачи и согласования резервов
    reports/                 себестоимость, сроки, замены
    settings/                реквизиты, пользователи, склады
  api/v1/export/[resource]/  выгрузка данных (JSON/CSV)
  login/                     вход
components/                  UI-кит, формы, загрузка файлов, подбор номенклатуры
lib/                         клиенты Supabase, форматирование, справочники ярлыков
supabase/
  migrations/                миграции по модулям (01–10)
  schema.sql                 всё одним файлом для SQL Editor
middleware.ts                обновление сессии и защита маршрутов
```

## 9. Ключевые правила, зашитые в базу (их нельзя обойти из интерфейса)

| Правило | Где реализовано |
|---|---|
| Жёсткий резерв только при предоплате или договоре с ключевым клиентом | `fn_can_hard_reserve`, триггер `trg_guard_reservation` |
| Нельзя зарезервировать больше свободного остатка | `trg_guard_reservation` |
| Снятие жёсткого резерва — только через согласование директора | `trg_guard_reservation`, `rpc_request_release`, `rpc_decide_release` |
| Запуск в цех запрещён без комплектующих | `rpc_advance_stage` + `fn_production_readiness` |
| Без отметки ОТК заказ не уходит дальше | `rpc_advance_stage` |
| Приёмка позиции, требующей сертификата, без его номера невозможна | `rpc_receive_po_item`, `receiveStock` |
| Падение ниже неснижаемого остатка создаёт задачу снабжению | `trg_stock_min_check` |
| Себестоимость пересчитывается при любом изменении спецификации | `trg_recalc_spec_items` |
